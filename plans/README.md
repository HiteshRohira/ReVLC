## Findings considered and rejected

- Command-line option blocklist (`cli.rs`) could be sidestepped by option
  spellings libVLC accepts: not a finding. Whoever controls the command line
  already controls the process; the list exists to protect the window, not
  as a security boundary.
- `REVLC_VLC_DIR` / `REVLC_VLC_ARGS` honoured in release builds: by design
  and documented in the README.
- Playlist files injecting libVLC options (`#EXTVLCOPT`, `<vlc:option>`):
  already handled. Items read from files are untrusted (`playlist_file.rs:88`)
  and libVLC ignores unsafe options for them (`vlc.rs:860`).
- Telemetry leaking names: `quality.rs` sends only source kind, scheme and a
  known extension, and has a test (`sources_without_names`).
- HTML sinks in the UI: none (`{@html}`, `innerHTML` not used).
- libVLC and FFmpeg downloads: versions pinned and checksums verified
  (`scripts/prepare-libvlc.sh`, `scripts/prepare-ffmpeg.sh`).
- Per-frame copy in the Linux memory video output (`vlc.rs` `gtk_display`):
  a known, documented limit of the experimental Linux build.

## Noticed in passing (no plan written)

- `cargo fmt --check` fails with about 500 diffs and nothing enforces a
  format. Any contributor or agent that runs `cargo fmt` will reformat the
  crate. Either add a `rustfmt.toml` that matches the house style or document
  "don't run it" in `AGENTS.md`.
- `Playlist::next_index` with shuffle on never returns "nothing left", so
  shuffle with Repeat Off plays on without end and `--play-and-exit` never
  quits under shuffle. A product question more than a bug.
- `updater.rs` (267 lines) has no unit tests; it is covered only by the
  Windows Sandbox update run.
